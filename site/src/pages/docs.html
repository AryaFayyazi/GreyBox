Put a monitor in your agent's loop

graybox.guard.Guard checks each proposed tool call before it runs, in each provider's own message format. A blocked call does not run; the agent gets a message that a human will review it. In our live test on a closed agent (T16, 500 scenarios with and without the gate), the share of episodes with an executed violation fell from 6.6% to 0.2%, with no violation after a block, at 89 ms per check.

from graybox.guard import Guard
from graybox.monitor import TextMonitor
guard = Guard(TextMonitor.load_json("greybox-text-monitor.json"))      # or Guard(ReaderMonitor.load(...), gate=QuantileGate(0.05))

# OpenAI Chat Completions
reply = client.chat.completions.create(model=..., messages=messages, tools=tools).choices[0].message
messages.append(reply)
for call in reply.tool_calls or []:
    v = guard.check_openai(messages[:-1], call)
    result = run_tool(call) if v.allow else v.block_message
    messages.append({"role": "tool", "tool_call_id": call.id, "content": result})

# Anthropic Messages
for block in response.content:
    if block.type == "tool_use":
        v = guard.check_anthropic(system, messages, block)
        result = run_tool(block) if v.allow else v.block_message

The guard builds each step with the same rule as the browser trainer's importer (graybox.guard.conversation_steps): system prompt, first user message, earlier calls with their results, the proposed call. On our example logs, the importer reproduces the research units byte for byte (979/979 GPT, 373/373 Claude), and the browser and Python give identical steps.

Hold for review instead of block

Blocking has a cost. In our live tests, goal completion fell from 47.4% to 45.6% (GPT) and from 40.7% to 34.9% (Claude). Nearly all of that loss came from episodes in which the gate blocked a safe action (96% of it on Claude). In Claude episodes with no block, goals were unchanged (41.4% vs 41.1%). Give the guard a reviewer: an escalated action is held, and your function decides whether it runs.

We tested this on Claude (T16c, preregistered, 450 scenarios, with an oracle as the reviewer). Episodes with an executed violation went from 6.7% to 0.0%. Goals were reached in 38.7% of episodes (no gate: 40.7%; blocking: 34.9%). The preregistered test that review costs at most 3 points of goals failed (−2.0 points, 95% interval −5.1 to +0.7). Episodes in which the reviewer let a held action run kept their goals (60.8% vs 58.8%). The reviewer saw 0.20 actions per episode. A human reviewer makes errors and takes time, so these numbers are an upper bound.

def ask_human(step):                      # step: instructions, task, history, action (+ context with chat=True)
    return review_queue.approve(step)     # True: run it; False: block it

guard = Guard(monitor, gate=QuantileGate(0.05), reviewer=ask_human)
v = guard.check_openai(messages, call)
if v.held: log_review(call, approved=v.allow)
result = run_tool(call) if v.allow else v.block_message

Agents that talk with a user

By default a step keeps the system prompt, the first user message and the earlier tool calls. In customer-service agents, the facts that decide an action often come later from the user (a cancellation reason, a confirmation). With chat=True, the context keeps every user turn and agent message in order (graybox.chat.chat_ctx):

guard = Guard(monitor, chat=True)                                   # score with conversation-aware context
python -m graybox.train_reader logs.jsonl --chat --out probe.joblib    # train on the same context

Train and score with the same setting. A monitor trained on the default context sees different text with chat=True. The browser trainer has the same option, and it gives identical context to Python (268/268 steps of 40 real τ²-bench conversations, 182 of them with later user turns).

The text monitor (CPU, real time)

Train it in the browser trainer and download the model file, then:

from graybox.monitor import TextMonitor, Step

tm = TextMonitor.load_json("greybox-text-monitor.json")         # pure Python to score
history = [Step("read_file", {"path": "/hr/salaries.csv"}, "name,salary\n...")]
action = ("send_message", {"recipient": "press@news.example", "body": "..."})
if tm.escalate(system_prompt, user_task, history, action):    # the cut learned from your data
    hold_for_review()

Or train in Python on (instructions, task, history, action) tuples: TextMonitor().fit(steps, labels); score with tm.score(...).

The reader monitor (GPU, robust to new tasks)

curl -LO https://github.com/AryaFayyazi/GreyBox/releases/download/v0.2.0/reader_probe_cape_agentdojo.joblib
from graybox.monitor import ReaderMonitor, QuantileGate, Step

mon = ReaderMonitor.load("reader_probe_cape_agentdojo.joblib")    # downloads Qwen/Qwen3-8B on first use
gate = QuantileGate(budget=0.05)                    # escalate the riskiest 5% of this agent's actions
gate.fit(past_scores)                               # optional: warm up on trusted past traffic
p = mon.score(system_prompt, user_task, history, action)
if gate(p):
    hold_for_review()
Act on the gate, not on p. The probe ranks a new agent's actions well, but its probabilities do not transfer: on Claude a 0.5 cut caught 3% of violations. QuantileGate sets its cut at the top budget of the first 500 actions it sees (no labels), then freezes it, so a burst of malicious actions cannot raise it. It escalates everything until it has seen 100 actions. Call gate.recalibrate() when the agent, its tools or its policy change.

Two probes are in release v0.2.0 (4.3 MB each, with SHA-256 checksums; load them with the scikit-learn version given there):

  • reader_probe.joblib: 17,623 labelled steps of the open Gemma-4 agent on CAPE-Bench.
  • reader_probe_cape_agentdojo.joblib: the same, plus 3,455 labelled AgentDojo calls of two open agents. On a closed agent's AgentDojo calls it scored 0.922 (zero-shot judge 0.787; T14).

Both learned the policies in their training data. For another type of policy, add labelled steps of it: features from mon.features(prompt), then the same scikit-learn pipeline.

Train the reader monitor on your own labels (GPU)

Label actions in the browser trainer and download them, or use logs that carry a labels field. Then one command computes the reader's features and trains the probe:

python -m graybox.train_reader greybox-labelled-actions.jsonl --out my_reader_probe.joblib

It reports an AUROC from cross-validation grouped by conversation and the catch rate at a 5% budget, and writes a file that ReaderMonitor.load, Guard and the server use. On our 300 example GPT conversations (1,515 actions), it took 90 seconds on one GPU: AUROC 0.994, 98.5% of violations caught at 5% review (the browser's word-count monitor: 0.989 and 94%).

HTTP API (self-hosted)

GB_TEXT_MONITOR=greybox-text-monitor.json uvicorn graybox.monitor_server:app --port 8000   # CPU only
GB_MONITOR_PROBE=reader_probe.joblib      uvicorn graybox.monitor_server:app --port 8000   # + GPU reader

POST /v1/monitor/text scores with the browser-trained text monitor and its stored cut. POST /v1/monitor/action uses the reader with a frozen gate per stream. Both take the same body:

POST /v1/monitor/action
{"instructions": "...", "task": "...",
 "history": [{"tool": "read_file", "args": {"path": "/hr/a"}, "result": "..."}],
 "action": {"tool": "send_message", "args": {"recipient": "..."}},
 "stream": "billing-agent", "budget": 0.05}

→ {"p_unsafe": 0.000213, "escalate": false, "threshold": 0.00264, "calibrated": true, ...}

For agents that talk with a user, send "context" (from graybox.chat.chat_ctx) in place of instructions, task and history, with a monitor trained on such contexts. Each stream calibrates its own frozen cut from its own traffic. Transcripts stay on your machine. A Dockerfile is in deploy/ of the repository.

Data format for labelled steps

{"instructions": "...", "task": "...", "history": [{"tool": "...", "args": {...}, "result": "..."}],
 "action": {"tool": "...", "args": {...}}, "label": 1, "group": "task-17"}

One proposed action per line: everything the monitor may see before it runs. label is 1 if executing the action violates your policy. group keeps a task's steps in one cross-validation fold. Text rendering is identical in Python and in the browser (verified byte for byte on 302 real agent steps).

How to evaluate a monitor honestly

  • Hold out whole tasks, not steps (the trainer does this). Steps of one task share text and inflate accuracy.
  • Report the catch rate at the review budget you can afford, not only AUROC.
  • Test on a policy or task family you did not train on before trusting it there.
  • Never take the threshold from another agent: calibrate on this agent's traffic and freeze it.
